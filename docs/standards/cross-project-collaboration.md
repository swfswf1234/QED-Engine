# 跨项目协作规范

状态：Current
最后更新：2026-08-30
确认状态：已确认
治理对象：三项目间的需求传递、评审、执行、验收回执与执行纪律
依据 ADR：`../history/adr/v0.1/0002-frontend-and-port-centralization.md`
关联测试：`tests/contract/test_cross_project_collaboration.py`

## 目的与边界

本标准是跨项目操作的唯一事实源。三个项目独立开发、独立部署，Axiom-Flow 与 QED-Tracker
是独立 git 仓库，本仓库不直接修改其代码。独立性铁律的完整定义见
[architecture/four-service-architecture.md](../architecture/four-service-architecture.md)。

适用范围：任何需要对方项目配合的改动（服务端口、数据目录、直读配置变量、接口对接、前端
迁移等）。纯本仓库内的改动不适用本标准，走[任务生命周期](task-lifecycle.md)。

## 强制规则

### 协作流程

1. **发起**：需求方在根仓库 `docs/trackers/todo.md` 登记请求任务（标注目标仓库与"请求"），
   变更涉及接口、端口、数据布局或契约时，在**对方项目**的 `docs/plans/` 建设计讨论文档
   （必要时先在对方仓库写 todo 请求条目）。
2. **评审**：用户评审对方仓库的计划文档与 todo 请求，确认方向；根仓库不直接修改对方项目
   代码。
3. **执行**：对方项目在自己的仓库内按自身 AGENTS.md 与门禁执行，由其 agent 或开发者完成
   （谁收任务谁执行）。
4. **验收回执**：对方完成并关闭其 todo 后，回到根仓库 todo 更新请求任务状态并记录证据
   （对方仓库的提交号/测试输出）。
5. **约束**：跨项目改动不得破坏独立性铁律；根仓库总台账保持与对方 todo 的一致性。

### 变更规模分级

| 规模 | 判定 | 必须产出 |
| --- | --- | --- |
| 接口/契约级 | 协议、端口、地址、字段、数据目录或配置事实源变化 | 对方项目计划文档 + 对方 todo 请求 + 根仓库登记 |
| 文案/操作级 | 文档措辞、命令示例、默认值说明 | 仅根仓库 todo 登记，可并入其他任务 |

### 计划文档模板

对方项目 `docs/plans/` 中新建的计划文档至少声明：需求方、目标项目、接口面（端口/变量/目录/
协议）、评审方（用户）、执行方（目标项目）与验收标准。对方 agent 评审通过后自行决定是否
晋升到 `docs/design/` 固定文档。

### 登记格式

根仓库 todo 的跨项目请求行：任务列标注"（请求：<目标项目>）"；证据/下一条件列记录对方仓库
todo 承接情况与回执。

### 执行纪律

#### 合法动作限定

需求方（根仓库，含其 agent 与派发的 subagent）在目标项目工作区的**合法动作仅限**：

| 动作 | 允许 | 说明 |
| --- | --- | --- |
| 读取 | ✅ | 代码/文档/测试只读，理解契约与现状 |
| 创建或修改其文档 | ✅ | plans/ 计划文档、todo 登记、指南等（不改变其代码行为） |
| **产生其代码改动** | ❌ | 任何 src/tests/配置代码改动必须由目标项目在其仓库内完成 |
| **git 提交与推送** | ❌ | 子项目仓库的 commit/push 一律不归需求方执行（含未提交改动存在时与用户上传指令场景），只读检查后报告状态，由用户或对方仓库执行（用户逐个授权例外时可代执行） |

#### 用户口头指令不豁免

「优化/改造某子项目服务」等指令同样走本流程——登记请求 → 对方建计划文档 + todo →
用户评审 → 对方执行 → 回执。

#### subagent 派发合规

需求方控制器在向子项目工作区派发任何任务前，先核对任务归属——属代码任务则改为登记请求流程，
不得直接派发写码。

#### 误产生的代码改动

登记移交（在对方 todo 标注"代码已由需求方误建在工作区（未提交），由贵方审阅后自行提交
或调整"），对方审阅后自行处理。

#### 子项目 git 操作边界

子项目的 **git 提交与推送一律不归需求方（根仓库 agent）执行**——即使其工作区存在未提交
改动（无论改动由谁产生）、即使「上传 GitHub」之类的用户指令包含子项目，根仓库 agent 也只做
只读检查（git status/log/diff 等）并向用户报告状态，提交/推送由用户或对方仓库自行执行；
用户明确逐个授权例外时才可代执行。

#### 跨项目诊断纪律

跨项目问题的诊断必须遵循**先只读排查，后登记请求**原则；禁止无证据归因。

##### 诊断三必查

在登记跨项目请求或向用户报告对方问题前，必须完成以下只读排查：

| 序号 | 必查项 | 方法 | 禁止行为 |
| --- | --- | --- | --- |
| 1 | 对方代码实际行为 | `grep` / `rg` 搜索对方仓库源码中相关函数的实际实现 | 凭记忆或假设断言对方"用了旧格式""没改" |
| 2 | 服务日志实际记录 | 查看对方服务运行日志中相关时间窗口的 HTTP 状态码与错误体 | 凭错误描述推断日志内容 |
| 3 | 配置实际生效值 | 核查 `.env` / 环境变量 / 配置文件中的实际值与传播链路 | 假设对方配置与自己不同或已过时 |

##### 禁止无证据归因

- 在 `todo.md` 证据列登记跨项目请求时，必须包含**实际日志片段、代码行号或配置值**作为
  证据，不得用"疑似""可能""估计"作为唯一依据。
- 若排查后仍无法确诊，标注"待对方协助排查"并附已排查证据，由对方在其环境下补全诊断。

##### 误判处理

被对方回执为误判时，根仓库 agent 必须：
1. 在 `completed.md` 记录误判原因分析（哪三项假设被证伪、真实现象是什么）；
2. 作为后续同类诊断的参考——遇到类似症状时先检查误判记录中的"真实现象"列。

## 执行与门禁

- 涉及子项目改造的请求在根仓库 todo 登记，目标项目在自己的 todo 承接并遵守其门禁；根仓库
  不直接修改子项目文件。
- 请求被对方拒绝或改期时，根仓库 todo 更新为 Blocked 并声明证据、恢复条件与责任位置。
- 本标准由 `tests/contract/test_cross_project_collaboration.py` 守护登记格式与设计文档模板
  的一致性；具体跨项目事实以双方 todo 与 Git 历史为准。

## 变更与取代

改变流程步骤、变更分级、登记格式或执行纪律时必须先新增 ADR。措辞、链接和不改变语义的
整理可直接修改本标准。子项目各自的协作流程以其自身 standards 为准；本标准作为三项目
协作的上游约定。
