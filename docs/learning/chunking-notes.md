# 文本切分笔记（Chunking）

个人学习资料，不参与工程治理。

## 为什么要切分

1. 模型上下文窗口有限，塞不下整本书。
2. 检索粒度：切得太粗，命中即冗余；切得太细，上下文碎片化，语义不完整。
3. 成本：只把相关片段送进模型，降低 token 消耗。

## 常见切分策略

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 固定长度 | 按 token 数硬切 | 快速原型 |
| 递归字符切分 | 按段落 → 句子 → 单词逐级切，直到满足上限 | 通用默认（LangChain 默认） |
| 语义切分 | 用嵌入相似度在句子边界处找"话题断裂点" | 长文、会议记录 |
| 结构切分 | 按 Markdown 标题、代码块、PDF 章节切 | 半结构化文档 |

## 关键参数

- `chunk_size`：块最大长度（按字符或 token）。
- `chunk_overlap`：相邻块重叠长度，避免切断关键句、丢失跨块上下文。
- `separators`：优先使用的分隔符顺序（如 `\n\n` → `\n` → `。` → 空格）。

## 数学文档的特殊性（QED 关注点）

- 公式不能被腰斩：切分点应避开 `$...$` 或 `\[...\]` 区间，否则公式语义断裂。
- 定理与其证明应尽量同块：引用定理时证明上下文常被检索命中需要。
- 符号定义（如"设 x ∈ R"）与后续使用距离远，单靠切分无法解决，需结合检索策略（见
  [RAG 笔记](rag-notes.md)）。

## 推荐经验值（起步）

- 通用中文段落：500–800 token/块，overlap 50–100 token。
- 数学/表格密集内容：降低到 300–500 token，避免块内混入过多公式。

## 验证方法

- 抽样查看切分边界是否截断完整句/公式。
- 用下游检索命中率与问答质量评估，不要只看长度分布。
