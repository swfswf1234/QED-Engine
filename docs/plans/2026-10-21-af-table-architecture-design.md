## 目标与成功标准

**目标**：把「文档解析管理 + 知识点梳理」两段功能所需的存储一次梳理定档——逐张判读用户提的四表与 LLM 日志在 `af_*` 现状里的对应物，给出必须表最小集与逐列形状（每列用处、键与索引、生命周期、与既有表的关系），并把解析正文是否入库、梳理工作区归属、跨仓提升通路三处代价写清，交用户在 1.0 前 schema 重建档位内一次裁死。

**定档（2026-10-21 同日第二批）**：本目标已闭合——用户裁决①~⑩与 Axiom-Flow PLAN-024 把上述三处代价全部答死，
**逐列形状正本移交对方 PLAN-024**，本壳退为指针（依据与差异清单见下节「逐列形状的地位」）。本节上段保留作立项时的
目标陈述，不再作为待办；本壳在册理由是「被否选项的证据＋根侧取证锚」，不是形状事实源。

**目标效果**：对方拿到本稿即可独立评审建表（其准入守则要求的判据与改动面齐备）；根侧拿到回执即可按表级变更同批随步总纲；「还有哪些表是必须的」这一问有成文答案而非临时补句。

**本壳不改动任何代码与库内数据**：根侧本轮只做取证、形状设计、登记与待裁。

### af_kp_edges（知识点关系边表）〔历史形状：用户裁决⑥不建此表，语义并入 `af_kp.links`〕

**一行＝两个节点之间一条有类型的关系**。为什么不能压进 `af_kp_nodes` 的 JSON 列：对方「JSON 列反向闸」明文「JSON 列不得承载需要唯一约束或集合检索的身份关系——某键一旦有此需求即为表级问题」（`:36-37`）。关系边同时需要唯一约束（同两端同 kind 不得重复）与反向集合检索（「哪些点以 X 为先修」），是教科书式的表级问题。

| 列 | 类型 | 空/默认 | 键 | 用处 |
| --- | --- | --- | --- | --- |
| `edge_id` | VARCHAR(64) | NOT NULL | PK | 确定性摘要 `afe_<md5(from_id:to_id:kind)[:12]>`。用确定性派生而非随机发放的理由与 `af_page_regions.region_id` 同源（`:256-259`）：重复声明同一关系必须命中同一行，否则并发提交各造一行、幂等要靠客户端记忆 |
| `from_id` | VARCHAR(64) | NOT NULL | UQ/i | 起点 `node_id`（逻辑引用本表，无物理外键）。应用层校验存在性 |
| `to_id` | VARCHAR(64) | NOT NULL | UQ/i | 终点 `node_id`。写入前归一（见下行） |
| `kind` | VARCHAR(24) | NOT NULL | UQ | 闭集：`prerequisite`=先学（from 必须先于 to，有向、参与 DAG）／`co_requisite`=需同时掌握（对称，写前按 `min,max` 归一端点序，使反向重复声明幂等命中）／`explains`=解释（from 解释 to）／`exemplifies`=举例（from 是 to 的例子）／`extends`=推广延伸（有向，参与 DAG）。用户原话的六项逐条映射见 R-3 |
| `note` | VARCHAR(1000) | NOT NULL `''` | — | 人工备注（关系为什么成立的一句话）。列名取单数 `note`，与族内较新的 `af_block_edits.note`／`af_page_regions.note` 同口径（`:224/:249`）；`af_books.notes` 的复数不一致属 REQ-133 R6 的范围，本表不重开该判 |
| `book_id` | VARCHAR(100) | NOT NULL | i | 冗余书坐标（由两端节点派生）。用处＝按书聚合读出全部边、删书按作用域带走。冗余的正当性有先例：`af_block_edits.book_id`／`job_id`／`page_no`／`block_index` 四列已全被 `edit_id` 摘要包含，仍逐列存（`:217-221`）——摘要只作身份，不作查询域 |
| `created_at` / `updated_at` | DATETIME | NOT NULL | — | UTC 时刻对 |

索引与键：`uq_af_kp_edges(from_id, to_id, kind)`、`ix_af_kp_edges_to(to_id, kind)`（反向先修查询）、`ix_af_kp_edges_book(book_id)`。

**服务端不变式（DDL 表达不了的三条，须在受理门成文并加守护）**：① `from_id != to_id`（自环一律 422）；② `prerequisite`／`extends` 两 kind 合起来必须**无环**——落库前对现有图做 DFS，成环即拒绝并在响应里回指环路径；`co_requisite`／`explains`／`exemplifies` 允许成环（它们不是次序语义），这一区分是「哪些边参与 DAG」的唯一口径；③ 两端节点必须同 `book_id`（跨书关系归根侧主表，不落本表）。

**生命周期**：随梳理推进增量写（一次全量声明式提交或逐边提交，见 R-6 的端点形状）→ 人工改名不碎边（身份是 node_id 不是 name）→ 节点删除时由应用层级联清边（无物理外键，故必须显式）→ 删书与 `admin/purge` 整体带走 → **不随解析版本更替删除**（同 `af_page_regions`）。

## 叙述分工与提升契约

**叙述分工（2026-10-21 改判，原案作废）**：本壳原判「结构＋摘要在 AF、长叙述归根侧候选池 `qe_kp_detail`」，**该分工已不成立**——同日 [REQ-132 W5](../history/plans/2026-10/2026-10-21-qe-family-rename-and-refactor.md) 判池**整表废弃**（取证：提升时丢弃 8 列、`map_seed`／`dedup_of`／`book_ref` 全仓零读、`confirmed` 从无 `WHERE` 命中）。现行分工＝**三处各存其份**：解析正文在文件系统，结构与一句总结在 `af_kp`，长叙述在 `QED_DATA_ROOT` 下的文件（`af_kp.narrative_ref` 只存根内相对路径，对方裁决⑧）。原设计意图「两池不互为备份、避免撞上『列不存正文与大字段』的改判需求」继续成立，只是叙述侧的承载方从根表换成 AF 的文件指针。

**提升（导出到共享主表）的方向与写权**（与对方 PLAN-024「提升通路」节同判，此处只记根侧承接面）：
